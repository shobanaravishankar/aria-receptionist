# The simulated appointment lifecycle (prototype)

An opt-in mode of the demo in which Aria can **find, book, move and cancel appointments and look up a client's last completed visit**, all in a local, invented calendar.
**Nothing in it is connected to Booksy or to any real salon calendar**, and nothing in it is a real client. The read-only demo (`demo-serve` without `--lifecycle`,
`demo-agent` without `--mode lifecycle`) is untouched and remains the default.

## What it is made of

| Part | Where | What it does |
|---|---|---|
| Store | `aria_booking/appointments/store.py` | One local SQLite file (git-ignored: `booking/.local/demo-appointments/`). Every change is one `BEGIN IMMEDIATE` transaction. |
| Calendar overlay | `appointments/overlay.py`, `demo/dataset.py` | Stored appointments are drawn through the single `DemoDataset.day_plan`, which the page AND the voice read driver both call: they cannot disagree. |
| Judge | `appointments/judge.py` | The one availability judgement, used for the read-back's dry run and again INSIDE the store's write transaction at the save. |
| Tools | `appointments/tools.py`, `tool_defs.py` | `find_appointments`, `last_completed_visit`, `book_appointment`, `cancel_appointment`, `reschedule_appointment` (plus the reviewed `lookup_service`, `check_slot`, `find_alternatives`). No Booksy route. |
| Owner alerts | `notify.py`, `sender.py`, `dispatcher.py` | A durable outbox, an injectable sender, a dispatcher and a worker. **No provider is built in.** |
| Seeds | `appointments/seed.py` | Three fictional clients with reserved 555-01xx numbers, so a test has something to find, change and cancel. |
| Prompt and tool file | `voice_agent_draft/prompt_template_lifecycle.md` -> `prompt_demo_lifecycle.md`, `tools_demo_lifecycle.json` | Generated by `python -m aria_booking.catalog.render --write`; a test fails if they differ. |
| Operator | `demo-agent --mode lifecycle ...` | The same create / update / verify / preflight / prepare-web, held to the lifecycle prompt and eight functions. |

## Design decisions (so each can be reviewed once)

* **Identity.** A stored appointment gets a 6-character reference (no 0/1/I/L/O) when it is created and keeps it for life, also when it is moved. Seeded rows derive theirs from a seed
  key, so a restart, a rebuilt file or a new day never renumbers anything. A reschedule moves the SAME row (version + 1); a cancel keeps the row (status `cancelled`, slot freed).
* **Atomic commit.** `BEGIN IMMEDIATE` serialises writers, so two callers racing for one slot are decided by the database. The judge runs inside that transaction on the
  transaction's own rows. The store also enforces, whatever the judge says: a technician and a client are never in two overlapping appointments.
* **Two steps, bound to the call.** Booking, cancelling and moving each begin with a read-back that saves nothing and returns a token tied to this call and to exactly what was
  read. A confirmation whose details differ, whose token belongs to another call, or that has expired gets a fresh read-back. The save is idempotent (key = call + token): a retried
  or repeated confirmation is answered from the first result. Success is claimed only after re-reading the store AND the shared calendar.
* **Stale confirmations.** Cancel and move carry the version that was read back; if the appointment changed since, nothing is changed and it is read back again.
* **One appointment, never another.** Cancel and move go by the reference AND the client's complete phone number; a wrong pair is simply "not found" (failures are capped per call); on a
  number shared by several records the name must match. Looking up never mutates anything and never queues an alert.
* **A phone number identifies a DEMO record; it is not authentication.** It is normalised without guessing digits, never spoken back, never logged, never returned. Names are used
  only to tell records that share a number apart.
* **Latest completed visit.** The reviewed history design over the store: only COMPLETED visits count; cancelled, no-show, upcoming and unknown-completion visits are excluded and an
  unknown newer visit blocks an older answer. **Convention (please review):** when the demo opens, a confirmed appointment whose time has passed is marked completed (the simulated salon
  is assumed to have done it); that never notifies anyone.
* **Buffers.** The cleanup time of the appointment being booked is checked at commit (as `check_slot` does). An existing appointment's own cleanup time is not blocked against a later start
  (the generated visits and the real calendar do not show it either).
* **No fees or policies.** No tool holds or states any cancellation fee, deadline or policy, and the prompt forbids inventing one. The cancel reason is optional and capped; cancelling never
  depends on choosing another time; if the caller says they are busy, Aria offers another day or time first.

## Owner alerts (Shobana's texts): what exists and what is still needed

Each committed booking, cancellation and move writes ONE row in the outbox, in the same transaction as the change (so a row exists only for a committed change). A move is **one**
coherent message with the old and the new time, not a cancellation plus a booking. Each message is marked `[Serenity prototype alert]`, names the client and the appointment (service,
technician, day and time, reference) and contains no phone number and no free-text reason. Creating a seeded row never sends anything; cancelling or moving one does.

Sending is a separate step that never undoes an appointment: the dispatcher claims a row atomically (so a retry, a second dispatcher or a restart cannot send twice), treats an unknown outcome as
"uncertain" and never retries it (a retry could text the owner twice), retries a definite refusal at most twice more, logs only the alert id and the result, and nothing is ever said to the caller about
delivery. The worker is woken by a commit and has no timer.

**Nothing can be sent yet.** What is needed from Shobana, and nothing has been provisioned or stored:

1. **The destination number** (her own mobile): put it in `booking/.local/owner_sms.json` as `{"to": "+1XXXXXXXXXX"}` (git-ignored) or in `ARIA_OWNER_SMS_TO`. It is refused if it is incomplete or in the
   reserved fictional range. It must never be given in chat, a commit or a shared log.
2. **A provider and its credentials.** No existing SMS setup was found in the repository. A provider account (for example a messaging API such as Twilio) is needed, with: an account identifier and secret
   (stored with `demo-agent store-secret`, encrypted, never in a file in Git) and a sending number or sender registered for US traffic (US long-code numbers need carrier registration, toll-free numbers need
   verification, and a trial account can usually text only numbers it has verified). Messages and a number cost money. Once she chooses a provider, a small `SmsSender` for it is added, tested against a fake HTTP
   transport, and enabled only by configuration.

Until both exist `demo-serve --lifecycle` says "owner alerts: NOT sent", and the alerts wait in the outbox.

## The salon-contact fallback

When Aria cannot answer, cannot confirm, or a service fails she says briefly what she cannot confirm and gives the salon's name and number. She never says a transfer, callback or message happened.
The name and number come from `aria_booking/showcase/config.py` (`contact_phone`, and `contact_name` if the spoken name should differ from the brand). **No number is configured**: the earlier template
held two numbers and neither is used. Until one is given, she says to contact the salon and gives none. When it is supplied: set it in `config.py`, run `python -m aria_booking.catalog.render --write`
(the knowledge section changes), and restart.

## Running it (nothing here is run by the code review)

```bash
python -m aria_booking demo-serve --lifecycle          # the calendar page + the signed tool endpoint, over the local store; seeds once
python -m aria_booking demo-agent plan --mode lifecycle  # what the agent would be held to (no network)
python -m aria_booking demo-agent verify --mode lifecycle
python -m aria_booking demo-agent prepare-web --mode lifecycle   # also writes test-instructions.txt with the seeded identities and the scenarios
```

`demo-agent update --mode lifecycle --confirm-update` changes the existing test agent's LLM in place, as before. It is a runtime change and waits for review.

## What is not claimed

How the model speaks this prompt, the speed of its answers and anything about a real call are unproven until a supervised call. The seeded dates are relative to the day the store was first opened (past
visits once; upcoming ones topped up as they pass). The demo date is fixed when the server starts. A quick tunnel is not durable hosting.
